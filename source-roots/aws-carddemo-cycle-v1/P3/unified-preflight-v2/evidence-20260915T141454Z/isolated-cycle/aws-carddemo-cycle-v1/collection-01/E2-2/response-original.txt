info:
  title: CardDemo Batch Transaction API
  version: 1.0.0
  description: |
    Contract for the individual CBTRN02C posting, CBACT04C interest-generation,
    and CBTRN03C reporting program boundaries. These are batch operations,
    not single-record services or an implementation of the complete JCL schedule.

    HTTP POST, JSON record projection, dataset-binding identifiers, and response
    status codes are chosen transport conventions. The COBOL programs define
    files, DISPLAY output, RETURN-CODE assignment, and calls to CEE3ABD, not HTTP.
    A binding identifies an already provisioned dataset in the execution
    environment; it does not create, load, validate, sort, or repair that dataset.
    Request record arrays represent sequential input files in the supplied order.

    Character fields are projected as strings, with shorter strings right-padded
    with spaces to their COBOL widths. Numeric fields represent valid numeric
    picture values, with implied decimal places projected as JSON numbers.
    Unknown character codes, blank identifiers, negative amounts, and non-calendar
    date text remain representable. There is no general business validation beyond
    the branches documented for each operation. Record fillers are preserved where
    they are supplied as input, but no initialized value is promised for output
    fillers that the program does not assign.

    Successful file changes are persistent. There is no evidenced transaction
    spanning files, rollback, retry policy, or idempotency guarantee. Failure can
    occur after earlier writes and account changes. Response artifacts are the
    files emitted by the invoked program, not evidence that a subsequent job ran.
x-uncertainties:
  - Execution requires a COBOL runtime, compatible file organizations, file bindings, and external termination support. Their availability is not established by the supplied source.
  - CEE3ABD is referenced but not supplied. The documented fatal branches attempt abend code 999 with timing 0; actual termination and delivery of an HTTP error depend on the execution environment.
  - Character encoding, collating sequence, signed DISPLAY numeric storage, and runtime file-status details are deployment concerns not fixed by the corpus.
  - Arithmetic uses receiving pictures without ROUNDED or ON SIZE ERROR. Fractional digits are discarded on ordinary decimal assignment; overflow outcomes and HTTP handling are not specified by the source.
  - TRANBKP, COMBTRAN, TRANREPT preprocessing, SORT, IDCAMS, and REPROC are schedule evidence only. No automatic backup, deletion, cluster definition, unload, merge, sort, or reload is included here. REPROC also references an unsupplied REPROCT control member.

    post:
      operationId: postDailyTransactions
      summary: Process one sequential daily transaction file
      description: |
        Invokes CBTRN02C. Processes records in input order, counting every
        successfully read daily record. XREFFILE is input, ACCTFILE and TCATBALF
        are I-O, and TRANFILE and DALYREJS are opened OUTPUT. In particular,
        TRANFILE is not opened EXTEND or I-O: preservation of an existing
        transaction master must not be assumed.

        Validation first looks up cardNumber in XREFFILE. INVALID KEY produces
        0100, INVALID CARD NUMBER FOUND, and skips account lookup. An account
        lookup INVALID KEY produces 0101, ACCOUNT RECORD NOT FOUND. Otherwise
        the program computes currentCycleCredit - currentCycleDebit + amount
        into S9(9)V99 and rejects with 0102, OVERLIMIT TRANSACTION, when that
        value exceeds creditLimit. It then compares account expiration text
        with the first ten characters of originalTimestamp. Expiration less
        than that text produces 0103, TRANSACTION RECEIVED AFTER ACCT EXPIRATION,
        overriding 0102 if both tests fail. Equality passes both comparisons.
        This is a character date comparison, not calendar validation. Account
        active status, cash limit, type/category membership, amount sign, and
        transaction-ID uniqueness are not business validation checks.

        Rejected records are written unchanged with a four-digit reason and
        76-character padded reason description to DALYREJS; processing continues.
        Completed runs with rejects assign RETURN-CODE 4, not an all-or-nothing
        failure.

        For an accepted record, all named daily transaction fields are copied
        except processingTimestamp, which is replaced by CURRENT-DATE formatted
        YYYY-MM-DD-HH.MM.SS.hh0000. TCATBALF is read using cross-reference
        account ID, typeCode, and categoryCode. A missing category balance is
        initialized and created with amount; an existing balance has amount
        added. Then amount is added to account currentBalance. Nonnegative
        amounts are added to currentCycleCredit; negative amounts are added,
        still negative, to currentCycleDebit. Finally the transaction is written
        to indexed TRANFILE keyed by transactionId.

        An account REWRITE INVALID KEY sets internal reason 0109 and ACCOUNT
        RECORD NOT FOUND after validation, but does not write a reject, increment
        the reject count, or prevent the transaction write. Do not interpret 0109
        as an ordinary returned validation rejection.
      x-preconditions:
        - Cross-reference input must be accessible as an indexed random file keyed by a 16-character card number.
        - Account and category-balance datasets must permit indexed random I-O; missing account and category records are permitted inputs with the documented distinct outcomes.
        - TRANFILE must permit indexed OUTPUT keyed by transaction ID; DALYREJS must permit sequential OUTPUT.
      x-persistent-effects:
        - Output-mode opening can initialize or replace TRANFILE and DALYREJS according to runtime semantics; this is not an append contract.
        - Accepted records change category balances, then accounts, then write transactions, in that order.
        - Duplicate transaction IDs are not prechecked. A non-00 indexed write status takes the fatal branch after earlier balance changes.

  /interest-generation-runs:
    post:
      operationId: generateInterestTransactions
      summary: Generate sequential system transactions from category balances
      description: |
        Invokes CBACT04C, not a standalone interest quote or a posting/merge job.
        TCATBALF is scanned in indexed sequential key order (account, type,
        category). At the first record of each account the program reads
        ACCTFILE and looks up XREFFILE by its alternate account-ID key.
        It reads DISCGRP using account group, source balance type, and category.
        Missing disclosure status 23 retries with group DEFAULT, padded to ten
        characters, retaining the same type and category. Missing default is
        fatal, not a zero rate.

        For each nonzero rate, monthly interest is
        categoryBalance * interestRate / 1200, assigned to S9(9)V99 without
        ROUNDED. Negative rates and balances are representable. A nonzero rate
        generates a record even if the computed amount is zero. A zero rate
        generates no record. Fees are explicitly unimplemented.

        Each generated transaction ID is the ten-character parameter followed
        by a six-digit counter, incremented before writing, beginning 000001.
        The parameter is not validated as a date and parameterLength is unused.
        Generated typeCode is 01, categoryCode is 0005, source is System,
        description begins "Int. for a/c " followed by the 11-digit account ID,
        amount is monthly interest, merchantId is zero, merchant name/city/ZIP
        are spaces, and cardNumber comes from the account-key XREF lookup.
        Both timestamps are the same CURRENT-DATE value formatted
        YYYY-MM-DD-HH.MM.SS.hh0000, not the parameter value.

        On transition to a new account, the previous account currentBalance is
        increased by its accumulated interest and both cycle totals are set to
        zero, even when its rates were all zero. The literal loop exits as soon
        as EOF is set: the ELSE intended to update at EOF is not reached.
        Consequently the final account is not rewritten, although its generated
        transactions are written. An empty balance file causes no account update.
        This contract does not repair that behavior.
      x-preconditions:
        - TCATBALF must be an indexed sequential input dataset; accounts must permit indexed random I-O.
        - XREFFILE must support random alternate-key account-ID lookup. INTCALC declares XREFFIL1 as an alternate-index path, but the program does not SELECT that name.
        - DISCGRP must support indexed random lookup by group/type/category; missing records remain representable fatal/fallback cases.
        - TRANSACT must permit sequential OUTPUT of 350-character transaction records.
      x-persistent-effects:
        - Creates or replaces the sequential TRANSACT output, mapped to SYSTRAN in INTCALC.
        - Rewrites only accounts reached by the account-transition update described above.
        - Does not update TCATBALF, post generated records through CBTRN02C, or merge records into a transaction master.
      x-uncertainties:
        - Alternate-key resolution and uniqueness depend on the provisioned XREF index; no selection rule for multiple cards per account is established.
        - Six-digit suffix exhaustion has no explicit error handling or uniqueness guarantee.
        - STRING does not initialize the whole transaction description or filler before writing; unassigned trailing content is not prescribed.
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [bindings, parameterDate]
              properties:
                bindings:
                  type: object
                  required: [categoryBalances, crossReferences, accounts, disclosureGroups, transactionOutput]
                  properties:
                    categoryBalances:
                      $ref: '#/components/schemas/DatasetBinding'
                    crossReferences:
                      $ref: '#/components/schemas/DatasetBinding'
                    accounts:
                      $ref: '#/components/schemas/DatasetBinding'
                    disclosureGroups:
                      $ref: '#/components/schemas/DatasetBinding'
                    transactionOutput:
                      $ref: '#/components/schemas/DatasetBinding'
                parameterDate:
                  type: string
                  maxLength: 10
                  description: PIC X(10) ID prefix; shorter transport text is space-padded. Example JCL supplies 2022071800. No date format constraint.
                parameterLength:
                  type: integer
                  minimum: -9999
                  maximum: 9999
                  description: PIC S9(4) COMP linkage field, never examined. If omitted, transport supplies the prefix length.
      responses:
        '200':
          description: Generation and closes completed; this does not imply the final account was updated or generated records were merged.
          content:
            application/json:
              schema:
                type: object
                required: [generatedTransactions, diagnostics]
                properties:
                  generatedTransactions:
                    type: array
                    description: Sequential TRANSACT output order.
                    items:
                      $ref: '#/components/schemas/Transaction'
                  diagnostics:

            Chosen mapping for a detected fatal execution failure. All non-00
            opens, closes, account reads/rewrites, XREF reads, generated writes,
            and unexpected category scan statuses take the abend branch.
            Disclosure lookup tolerates only 00 or initial 23; the default read

  /transaction-report-runs:
    post:
      operationId: generateTransactionReport
      summary: Produce the fixed-width transaction detail report
      description: |
        Invokes CBTRN03C on a supplied sequential transaction file. Reads just
        the first DATEPARM record, taking positions 1-10 as start text and 12-21
        as end text. Separator and remaining positions have no validation.
        Empty DATEPARM sets EOF and skips transaction processing; later
        parameter records are ignored. Date text, reversed ranges, and empty
        transaction input are representable.

        Only transactions whose processingTimestamp first ten characters compare
        inclusively between the two parameter texts enter report processing.
        Nonmatching records use NEXT SENTENCE to skip the rest of the loop body.
        No calendar parsing occurs. Input is not sorted by the program.
        The TRANREPT JCL separately proposes an unload, a card-number sort,
        and a date filter with hard-coded dates; none is performed by this
        operation, and those dates are not substituted for DATEPARM.

        On a change of included card number, the program prints the previous
        running "Account Total" when not first-time and looks up the new card
        in CARDXREF. This groups contiguous cards, not distinct account IDs.
        Each included transaction requires type and type/category lookups.
        Details contain transaction ID, XREF account ID, type code with the
        first 15 description characters, category code with the first 29
        description characters, source, and edited amount.

        Headers identify DALYREPT / Daily Transaction Report and the supplied
        date texts. Every physical record is 133 characters, space-padded as
        necessary. Detail amounts use -ZZZ,ZZZ,ZZZ.ZZ; totals use
        +ZZZ,ZZZ,ZZZ.ZZ. Four header lines are written initially. The page
        test is MOD(lineCounter, 20) = 0 before adding a detail, after the
        initial headers. Counter increments include headers, detail lines,
        account totals and their separator, and page totals and their separator;
        this is not a guaranteed 20-details-per-page rule. Page totals feed
        grand total and reset the page amount. Card-change account totals reset
        only the account amount.

        EOF handling is literal, not corrected accounting: the date comparison
        still runs after the failed transaction read. If the retained transaction
        buffer passes that comparison, the EOF branch adds TRAN-AMT again to
        page and account totals, then prints page and grand totals. It does not
        print a final account total. If retained date text does not pass, those
        final totals are skipped. Empty input and buffer contents after failed
        READ are runtime-sensitive; correct mathematical totals are not promised.
      x-preconditions:
        - CARDXREF, TRANTYPE, and TRANCATG must be accessible indexed random input datasets with the keys described in the supplied copybooks.
        - TRANREPT must permit sequential OUTPUT. Input grouping by card is needed for consolidated contiguous-card totals but is not validated or imposed.
      x-persistent-effects:
        - Creates or replaces TRANREPT; transaction and lookup files are read-only.
      x-uncertainties:
        - The last transaction buffer after EOF is not initialized by the program. Retention can cause the last amount to be counted twice in final page/grand totals.
        - A first included card consisting entirely of spaces equals the initial current-card value and skips the initial XREF lookup, leaving the account projection dependent on uninitialized lookup storage.
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [bindings, transactions, dateParameterRecords]
              properties:
                bindings:
                  type: object
                  required: [crossReferences, transactionTypes, transactionCategories, reportOutput]
                  properties:
                    crossReferences:
                      $ref: '#/components/schemas/DatasetBinding'
                    transactionTypes:
                      $ref: '#/components/schemas/DatasetBinding'
                    transactionCategories:
                      $ref: '#/components/schemas/DatasetBinding'
                    reportOutput:
                      $ref: '#/components/schemas/DatasetBinding'
                transactions:
                  type: array
                  items:
                    $ref: '#/components/schemas/Transaction'
                dateParameterRecords:
                  type: array
                  description: DATEPARM sequential 80-character records; only the first is read. An empty array represents EOF.
                  items:
                    type: string
                    maxLength: 80
                    description: Right-padded to 80 characters; start at positions 1-10, ignored character at 11, end at 12-21.
      responses:
        '200':
          description: Report program completed, possibly producing an empty report.
          content:
            application/json:
              schema:
                type: object
                required: [lines, diagnostics]
                properties:
                  lines:
                    type: array
                    description: Exact ordered TRANREPT records, without transport newline delimiters.
                    items:
                      type: string
                      minLength: 133
                      maxLength: 133
                  diagnostics:
                    $ref: '#/components/schemas/Diagnostics'
        '400':
          $ref: '#/components/responses/TransportRejection'
        '500':
          description: |
            Chosen mapping for a detected fatal execution failure. Non-00 opens,
            closes, report writes, and unexpected sequential read statuses take
            the abend branch. INVALID KEY on card, type, or category lookup
            displays the invalid key and status 23, then attempts abend rather
            than producing an unknown-description detail or per-record reject.
            Lookup paragraphs do not independently classify every other status.
            Partial report output can persist.
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/ExecutionFailure'
