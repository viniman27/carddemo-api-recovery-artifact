info:
  title: CardDemo Batch Transaction API
  version: 1.0.0
  description: |
    Contract for the program boundaries of CBTRN02C (posting), CBACT04C
    (interest generation), and CBTRN03C (reporting). Each POST represents one
    batch program invocation, not an individual transaction or an entire job schedule.

    HTTP paths, JSON serialization, and status codes are chosen transport
    conventions, not COBOL behavior. Request arrays supply sequential input
    files in array order. Indexed master files are environment-provided
    persistent dependencies, not implicitly created from requests. Output
    arrays expose records written by the program. No sorting, backup, merge,
    load, retry, rollback, or atomic commit is included.

    Character fields are transported without trimming; shorter strings are
    right-padded with spaces to their COBOL picture width. Numeric identifiers
    are digit strings preserving leading zeroes. Decimal numbers represent
    valid numeric picture values, including negative amounts and rates.
    No calendar-date, card-number, transaction-type, or category validation is
    imposed unless described for the particular program. Empty arrays and
    unknown keys remain representable.

    Runtime-generated timestamps use YYYY-MM-DD-HH.MM.SS.hh0000, derived from
    CURRENT-DATE without a transported timezone. They are not RFC 3339 values.
x-preconditions:
  - The COBOL programs, copybooks, file runtime, and file assignments must be available.
  - Indexed files must support the declared keys and open modes; sequential files must support their record lengths.
  - Each invocation needs fresh program working storage equivalent to a batch execution.
x-uncertainties:
  - |
    CEE3ABD is referenced but not supplied. Error branches display diagnostics
    and call CEE3ABD with code 999 and timing 0; actual termination and runtime
    error delivery depend on that external service.
  - |
    Arithmetic uses fixed pictures without ON SIZE ERROR or ROUNDED. Fractional
    digits are discarded on assignment rather than contractually rounded to
    nearest. Overflow, invalid physical numeric encodings, character encoding,
    and compiler/runtime-specific file behavior are not specified here.
  - |
    JCL is dependency and orchestration evidence, not proof of execution.
    TRANBKP uses REPROC and IDCAMS to back up and recreate the transaction
    master. COMBTRAN sorts backup and system transactions by ID and loads them
    with IDCAMS. Neither is invoked by these operations. REPROC references
    REPROCT control input that is not supplied.
  - |
    TRANREPT JCL unloads, filters processing dates, and sorts card numbers using
    ZD, although COBOL card numbers are X(16). It contains duplicate STEP05R
    labels. This contract does not execute that preprocessing or exclude
    nonnumeric card values.
paths:
  /transaction-postings:
    post:
      operationId: postDailyTransactions
      summary: Process the daily transaction input in sequence
      description: |
        Executes the CBTRN02C boundary. DALYTRAN is sequential input; XREFFILE is
        indexed input by card number; ACCTFILE and TCATBALF are opened I-O.
        TRANFILE is indexed by transaction ID but is opened OUTPUT, not I-O or
        EXTEND. DALYREJS is sequential OUTPUT. Consequently this is not a
        promised append-to-existing-master operation; opening OUTPUT can
        initialize or replace the output according to the file runtime.

        For each daily record the validation reason is cleared. An invalid-key
        cross-reference read gives 0100 and skips account validation. An
        invalid-key account read gives 0101. For an account found, temporary
        balance = currentCycleCredit - currentCycleDebit + amount, held in
        S9(9)V99. A credit limit smaller than that result gives 0102. Then
        expirationDate is compared as characters with originalTimestamp(1:10);
        expirationDate smaller than that prefix gives 0103, overwriting 0102
        if both fail. Equality passes both comparisons. Account active status,
        cash credit limit, type and category existence are not validated.

        A rejected record is copied to DALYREJS with its four-digit reason and
        76-character padded description, and processing continues. The
        processed count includes accepted and rejected input records.
        RETURN-CODE is explicitly set to 4 if any rejects occurred; the
        no-reject branch does not explicitly assign RETURN-CODE.

        For an accepted record, fields are copied to the transaction output,
        except processingTimestamp is replaced with the current timestamp.
        First the category balance keyed by mapped account, type and category
        is created from initialized data if missing (status 23), or incremented
        by amount if present. Next amount is added to account currentBalance.
        Nonnegative amount is added to currentCycleCredit; negative amount is
        added, still negative, to currentCycleDebit. Finally the transaction
        is written to TRANFILE. These actions are ordered and not atomic.

        Account REWRITE INVALID KEY sets internal reason 0109, "ACCOUNT RECORD
        NOT FOUND", but does not enter the reject-writing branch or increment
        the reject count: the transaction write still follows. There is no
        duplicate-ID business validation. A failed transaction write, including
        an indexed duplicate-key failure, takes the fatal I/O path after the
        earlier balance update attempts.

  /interest-transaction-generations:
    post:
      operationId: generateInterestTransactions
      summary: Generate system interest transactions from category balances
      description: |
        Executes the CBACT04C boundary. Reads TCATBALF sequentially in indexed
        key order (account, type, category); reads ACCTFILE by account and
        XREFFILE by its alternate account key at account changes. ACCTFILE is
        opened I-O; TCATBALF, XREFFILE and DISCGRP are INPUT. TRANSACT is
        sequential OUTPUT, separate from the posting program's indexed
        TRANFILE. Generated transactions are not posted or merged by this
        operation, and category balances are not modified.

        For each category balance, look up the account group, type and category
        in DISCGRP. Status 23 causes a second lookup with group "DEFAULT"
        space-padded to ten characters and the same type/category. A missing
        default is fatal. A zero rate produces no transaction. For any nonzero
        rate compute monthlyInterest = categoryBalance * interestRate / 1200,
        assigned to S9(9)V99 without ROUNDED. Generate a transaction even when
        that computed amount is zero or negative; add it to an S9(9)V99 account
        interest accumulator. Fee computation is an empty paragraph.

        Generated IDs concatenate all ten parameter characters and an
        incrementing six-digit suffix starting at 000001. Type is "01",
        numeric category is 0005, source is "System", description begins
        "Int. for a/c " followed by the eleven-digit account ID, amount is the
        computed interest, merchant ID is zero, merchant name/city/ZIP are
        spaces, and card number comes from the account-key cross-reference.
        Both timestamps are the current runtime timestamp.

        At each change after the first account, add accumulated interest to
        the previous account currentBalance, clear its currentCycleCredit and
        currentCycleDebit, and rewrite it. Critically, the apparent EOF update
        ELSE branch is not reached by normal loop flow: the read sets EOF
        inside the other branch and the loop exits. The last account is not
        rewritten. With one account, interest transactions can be generated
        with no account update; empty input generates no transactions and
        rewrites no account.

  /transaction-reports:
    post:
      operationId: generateTransactionReport
      summary: Produce fixed-width transaction report records
      description: |
        Executes the CBTRN03C boundary, not TRANREPT JCL. The request supplies
        sequential TRANFILE records and DATEPARM records. Only the first
        DATEPARM record is read: positions 1-10 are start date, position 11 is
        ignored, and positions 12-21 are end date. EOF on DATEPARM ends
        processing without reading transactions. Dates are compared as
        characters, not validated as calendar dates; reversed ranges are
        representable and not rejected.

        The program compares processingTimestamp(1:10) inclusively to the
        range. An out-of-range record executes NEXT SENTENCE, skipping the
        remainder of the loop's sentence. No sorting occurs. Contiguous card
        changes, not account-ID changes, trigger an "Account Total" and a new
        cross-reference lookup. Supply card-grouped input for conventional
        grouping; ungrouped input remains representable and yields repeated
        groups. Type and type/category descriptions are looked up for every
        included detail. Unknown lookup keys take the fatal branch.

        Output is TRANREPT opened OUTPUT, with 133-character records.
        Detail fields are transaction ID, mapped account ID, type code and
        first 15 description characters, four-digit category and first 29
        category-description characters, source, and amount edited as
        -ZZZ,ZZZ,ZZZ.ZZ. Headers use DALYREPT, Daily Transaction Report,
        the range and column labels. Total amounts use +ZZZ,ZZZ,ZZZ.ZZ.

        The first detail emits four header records. Before each detail, a page
        break occurs only when lineCounter modulo 20 is zero. Headers, totals
        and separator lines increment the counter as coded, so twenty is not
        a guaranteed number of details or an enforced maximum page length.
        Page totals are added into the grand total and reset. Account totals
        reset on card changes and do not contribute separately to grand total.

        EOF is checked after the date comparison. When the EOF iteration
        passes that comparison, the program adds TRAN-AMT again to page and
        account totals, then writes page and grand totals, with no final
        account total. If the read buffer retains the last included record,
        its amount is therefore counted twice in the final totals. If the
        retained record is outside the range, NEXT SENTENCE skips final
        totals. Do not interpret the output as a corrected aggregation.
        Empty input buffer behavior and EOF buffer contents are runtime
        dependent; this contract preserves report lines rather than promising
        normalized totals.
      x-dependencies:

          recordSchema:
            $ref: '#/components/schemas/TransactionCategory'
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              additionalProperties: false

              properties:

                  type: array
                  items:
                    $ref: '#/components/schemas/Transaction'
                dateParameterRecords:
                  type: array
                  description: Sequential 80-character DATEPARM records; empty means immediate EOF. Extra records are ignored.
                  items:
                    type: string
                    maxLength: 80
                    description: Right-padded to 80 characters. No separator, date-format or date-order validation.
                    examples: ['2022-01-01 2022-07-06']
      responses:
