# Steering Principles

Steering files are project memory, not exhaustive specifications.

In this project, steering exists to preserve the stable logic, priorities, vocabulary, and methodological identity of a master's research workflow on COBOL legacy modernization using a specification-driven pipeline.

They must help the framework remember how this project thinks.
They must not try to replace the specs, the evidence artifacts, or the research study text itself.

---

## Project Identity

This is not a generic product-development workflow.

This project is a master's research proof of concept focused on:

- COBOL legacy understanding
- AI-assisted knowledge extraction
- structured intermediate specifications
- API-oriented incremental modernization
- adapter-oriented integration
- semantic validation based on observed behavior

The central pipeline of the project is:

COBOL legacy -> AI-assisted extraction -> structured specification -> API contract -> adapter behavior -> semantic validation

All steering content must reinforce this progression.

---

## Content Granularity

### Golden Rule
> If a downstream artifact can be regenerated from stable project logic, steering should capture the logic, not the artifact itself.

### Steering should document
- stable methodological principles
- stage boundaries in the pipeline
- capability-first analysis rules
- evidence-before-interpretation discipline
- semantic reconstruction priorities
- artifact taxonomy
- traceability expectations
- rules about when implementation is allowed
- project vocabulary and preferred conceptual distinctions

### Steering should avoid
- exhaustive feature descriptions
- complete file listings
- full artifact contents
- detailed implementation logic
- one-off experimental outputs
- raw generated code as authoritative memory
- tool-specific noise unless it affects research behavior
- exhaustive documentation of internal automation metadata

### Example comparison

**Bad** (spec or implementation masquerading as memory):
```markdown
- validator.js validates CREDIT, DEBIT, TOTAL
- pipeline.js dispatches to handlers
- tests/pipeline.test.js covers error paths
```

**Good** (stable logic preserved as memory):
```markdown
- Validation logic derived in the proof of concept must remain traceable
  to the capability semantics spec, never to implementation convenience.
- Generated implementation files are auxiliary until the corresponding
  specification stage is mature and reviewed.
```

The bad example records file inventory that will drift and can always be regenerated by reading the repository.
The good example records the reasoning that must survive across sessions, artifacts, and pipeline runs.

## Steering vs Specs

Steering and specs answer different questions and must not be conflated.

| Concern | Steering | Specs |
|---------|----------|-------|
| Question answered | "How does this project think?" | "What is true about this capability/artifact?" |
| Stability | Long-lived, rarely changes | Evolves with each pipeline stage |
| Scope | Project-wide | Single artifact or capability |
| Authority | Methodological | Evidential and semantic |

If content is capability-specific, evidence-specific, or stage-specific, it belongs in a spec.
If content expresses a rule that would apply to the next capability as well, it belongs in steering.

## Maintenance Discipline

### When to update steering
Update steering only when one of the following occurs:

- a methodological rule has genuinely changed or been refined
- a recurring mistake reveals a missing rule
- the artifact taxonomy or stage boundaries evolve
- project vocabulary is clarified in a way that affects future artifacts
- a validated lesson from the proof of concept must be preserved for the institutional case

### When not to update steering
Do not update steering to record:

- the completion of individual tasks
- the contents of a newly generated artifact
- transient experiment results
- one-off decisions that will not recur

### Update quality rules
- keep each steering file readable in full as project memory
- prefer refining an existing section over appending redundant ones
- remove content that has become false rather than layering corrections on top
- preserve the separation between `product.md` (why), `tech.md` (with what), and `structure.md` (how organized)

---

## Security and Sensitivity

Steering files are loaded into every session and may be shared in research contexts.

Therefore:
- never store credentials, tokens, or institutional secrets in steering
- when the institutional legacy case begins, keep identifying details of institutional systems out of steering unless explicitly cleared
- prefer describing institutional constraints abstractly (e.g., "the institutional system has stricter persistence requirements") over quoting institutional material

---

## Desired Outcome

Good steering in this project should allow a new session — or a new researcher — to:

- understand the research pipeline and its stage boundaries without re-deriving them
- know which artifact types exist and in which order they mature
- apply evidence discipline and traceability rules consistently
- avoid premature implementation without being told again
- produce artifacts that remain defensible in the research study

If steering grows so large that it cannot be read as memory, it is failing.
If it is so thin that stage discipline must be re-explained each session, it is also failing.
Steering succeeds when it makes the project's methodological identity durable and cheap to recall.
